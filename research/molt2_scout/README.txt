Molt2 Scout: separate component experimenter (UNVALIDATED PROTOTYPE)

CLI method: molt2_scout. No paid Scout run, real model preflight or task evaluation
has been launched. Offline tests establish integration properties, not better
optimization performance or publication-level novelty.

Architecture:
- Native Molt architecture and dedup prompts pass through unchanged. Protected
  redesign/probation logic is inherited, and unsolicited measurement fields in
  native directions are not harvested.
- A separately metered experimenter can ask one component question per executed
  intervention, at most twice. It may decline. Every question is bound to an
  actual native direction/child and an established full-validity source anchor.
  The anchor must be that child or its source descendant: no ancestor or other
  branch substitutes. Recheck before charging a question, accepting its reply,
  queueing a probe and dispatching its evaluation. Native protected probation
  remains unchanged; questions wait until a target is established and competitive.
- Only anchors within the native probation-margin fraction of the observed
  fully valid frontier are eligible. Recheck at probe dispatch; an obsolete
  question loses its spent question call and gets no free replacement.
- Matched OFF/ON probes reuse the tested source/context/ownership registry.
  Results with validity below1 are inconclusive for mechanism learning.
  Negative observations remain local, not bans on an algorithm family.

Default limits retained:80 candidate-slot reservations including seed, run-dollar
cap0.50, native-dollar headroom0.10. Questions AND templates share the existing
4 diagnostic model-call reservations. Normal Scout operation therefore allows
at most2 pairs (4 evaluated probe arms), leaving at least76 native slot capacity.
Failures conservatively consume reservations. This is not a guarantee of76
successful evaluations. Probe/question cost threshold0.05 is an observed soft
threshold; the caller's SDK guard remains authoritative for total spending.

Question calls use the same model/provider configuration, ordinary reasoning off
and at most4096 output tokens. Native planner settings remain untouched. Prompts
include the executed direction text, source hash, verified public child score,
anchor code projection and conditional evidence. Source/record projections are
bounded and labelled; full recorded question/reply evidence is checkpointed.

Before any fresh benchmark: freeze a new protocol and use the corrected runtime
status runner for ALL methods. Do not alter or relabel the already-running
Decision replication. Preserve its original primary results and independent
runtime audit. Do not treat saved older controls as fresh corrected-harness
searches. Fresh paid launches need budget admission under the shared ledger.
